現在の実装と構成図

v1.3では現在のローカル実装を反映。Node.js 24・SQLite・ローカルファイルで動作し、外部サービスは使用しない。Cookieはブラウザの識別であり、メール本人確認ではない。操作手順は README を参照。

追加のローカル処理：ClamAVでファイルを検査し、LibreOffice・Popplerで画像キャッシュを生成する。模擬領収書はSQLiteの購入時データから表示・HTML保存・印刷する。手順は ローカル運用手順 を参照。

現行API

GETもブラウザセッションを利用します。更新処理はセッションAPIのCSRFトークンを付けます。エラー形式は { code, message, requestId, details? }、ヘッダーは X-Request-Id。確認番号を画面とerrors文書へ記録します。取得トークンをエラー記録へ残しません。400入力不正、401管理パスワード不一致、403権限・CSRF、404不存在・所有者不一致・権限停止、409失効・変更・競合、413サイズ超過、429回数制限、500処理障害を返します。購入履歴・管理注文・監査は { items, nextCursor }。limitは既定20・最大100。日時降順とID降順によるSQLのキーセット方式で、同時刻の行も欠落・重複しません。cursorは日時とIDのBase64url JSONで、不正な値は400です。

状態と業務処理

  1. カートの商品IDとクーポンから10分有効の見積もりを作成する。数量1、セットと単品の重複は拒否する。
  2. 利用規約・返金条件への同意後に模擬決済を要求する。規約版は local-2026-10-01。
  3. 商品の公開状態・revision・ファイル版・価格・クーポン上限を再照合する。変更・失効時は409で再確認を要求する。
  4. failureは402を返し注文を作らない。successはpaid注文・明細・規約同意・予定通知を同じトランザクションで保存する。実際の入金は照合しない。
  5. 同じ操作キー・本文の再送は同じ注文を返す。キーが同じでも本文が異なる場合は409。同じ見積もりの別キー消費も拒否する。
  6. ダウンロード発行時と取得時に同じブラウザのpaid注文を確認する。APIトークン方式であり、外部ストレージの署名付きURLではない。
  7. 管理者の模擬返金はpaid → refunded。理由・時刻・監査・予定通知を保存し、発行済みトークンを削除する。返金済みの再要求は返金を繰り返さない。実決済の返金要求中・失敗・異議申し立ては未実装。

商品はdraft／published／stopped。問い合わせはopen／handling／closed。通知はpending → savedで、5秒周期に期限の到来した予定通知を処理します。失敗の模擬では指数バックオフ、最大8回でfailed。手動retryでpendingへ戻します。savedは「ローカル保存完了」であり「外部メール送信成功」ではありません。通知IDは購入・返金・問い合わせごとに固定して重複作成を防ぎます。

クーポンは期限・割引率・利用上限をサーバーで判定し、注文と同じトランザクションで消費します。返金しても利用回数は戻しません。全paid注文を対象に購入済みを判定し、商品画面から元の注文へ案内します。セット内の一部でも購入済みなら重複購入を拒否します。見積もり時と注文確定時の両方で確認し、古い見積もりによる再購入も防ぎます。返金・リセット後は対象から外れます。

保護・運用・移行

  • CookieはHttpOnly・SameSite=Strict。ローカルHTTPのためSecure属性は未設定。本番HTTPS対応は今後の実装。
  • 回数制限はメモリ上の1分窓。セッション全体300回、ログインは接続元IPで10回、問い合わせはセッション5回・IP30回、ダウンロードは発行と取得合算で30回、アップロード10回、分析60回。再起動でカウンタはリセットされる。
  • PPTXは50MB、ZIP展開合計100MB、1500エントリ、1〜200ページまで。マクロ・埋め込みファイル・危険なパスを拒否し、未検証のSVGはアップロードしない。ClamAV接続を実装。autoは実行ファイル不在なら未検査、requiredは未完了を拒否、offはdisabledとして記録する。定義不足・実行失敗は503、問題検出は400で登録を拒否する。既存の同じ版の検出結果も記録し、infectedは購入・公開・ダウンロード・プレビューを拒否する。
  • 初期SQLite版の注文には現在のファイルで版を固定する。過去時点の版は復元できない。既存Cookieを引き継ぐが、localStorageだけのデモ注文は移行しない。
  • リセットは自分のorders・items・取得トークンを削除し、orderMetaをresetにする。通知・問い合わせ・監査・お気に入りは残す。
  • npm run backup は稼働中もSQLiteのバックアップAPIを利用できる。npm run restore -- バックアップ名 と npm run admin:reset はサーバー停止後に実行する。復元前に現在のデータも退避する。
  • 復元はDBとファイルのSHA-256、SQLite整合性・外部キー、商品と購入時ファイルの存在を検証する。バックアップにはDB内の管理資格情報も含むが、パスワードの平文ファイルは含まない。復元後に平文ファイルとDBの資格情報が異なる場合はadmin:resetで再発行する。
  • SHOP_DATA_DIR、SHOP_FILE_DIR、SHOP_BACKUP_DIR で保存先を指定できる。LOCAL_ADMIN_PASSWORD と LOCAL_EDITOR_PASSWORD は資格情報の初回作成時のみ参照する。機密値をGitへ保存しない。
  • 商品別SEOはビルド時点の公開商品から生成する。DBが未初期化ならJSONを使う。既定のrobots.txtは全体のクロールを禁止。SITE_URLを指定したビルドでは通常のサイトマップを生成するが、これだけで本番運用の準備が完了するわけではない。
  • 自動バックアップは5秒周期の確認で初回と以後24時間ごと、直近7件を保持。停止中は実行しない。SHOP_BACKUP_INTERVAL_MS=0 で無効、SHOP_BACKUP_KEEP は1〜365。自動分のみ削除し、手動分は保持する。失敗時は最大5分後に再試行し、maintenance文書と運用画面で状態を確認する。
  • バックアップはMFA秘密情報も含む。TOTPのローカル確認は npm run admin:otp（editorは -- editor）。同じ端末の生成は独立した第二要素ではない。紛失時のadmin:resetはMFA・復旧コードと管理セッションも解除する。
  • 外部参照・XML実体を変換前に拒否する。変換はシェルを使わず実行し、各ツール90秒で打ち切る。管理APIの処理は同時に1件、競合はASSET_BUSY。変換は一時プロファイルでマクロを無効化するが、OS隔離は未実装。
  • npm run backup:list で一覧、backup:check -- 名前 で検証、restore:drill -- 名前 で一時領域へコピーして再検証する。稼働中のデータは変更しない。画像キャッシュはバックアップ対象外、必要なら復元後に再生成する。
  • ツール設定・検査モード・定義準備・復元確認は ローカル運用手順 を参照する。

検証と今後の拡張

01 目的と範囲（本番向け設計）

現在の模擬購入を、実際の入金確認と購入権限に基づくダウンロード販売へ拡張する。対象は単一店舗・日本国内向け・日本円のデジタル資料販売。配送・在庫管理・定期購入は対象外とする。

現在のローカル実装は冒頭の「現在の実装」と「現行の画面・データ・API」に記載する。01〜11は実販売に向けた将来の目標で、全項目が実装済みという意味ではない。サービス契約、実際の課金、本番公開は実施していない。

初期リリースの前提

  • 購入前にメール認証。数量は1固定、支払方法はホスト型のカード決済から開始する。
  • 税込価格を表示し、金額は円の整数で管理する。税区分・端数処理は事業者の条件に合わせて確定する。
  • 注文に商品名・価格・利用許諾・ファイルのバージョンを記録する。
  • 初期版の返金は注文全体の全額返金。商品単位・部分返金は後続拡張とする。
  • 公開停止後も購入済みバージョンを再取得できる設計を基本とする。提供期間は販売条件で明示する。

ローカル実装から本番へ

商品・注文のサーバー保存、カートのみのlocalStorage保存、PPTXの非公開化はローカルで実装済み。今後は購入者のメール認証、実決済とWebhook、PostgreSQL等の本番DB、非公開オブジェクトストレージ、外部配信へ置き換える。模擬購入から実販売の購入権限は発行しない。

フロントエンドはReact・TypeScript・Viteを継続利用する。バックエンドはNode.js・TypeScript、データベースはPostgreSQL、ファイルはS3互換の非公開オブジェクトストレージ、決済はStripe Checkoutを候補とする。認証・メール配信・実行基盤の事業者は未確定。

05 業務フローと状態（本番向け設計）

購入と入金確認

  1. APIが商品IDから公開状態と価格を読み、短時間有効の見積もりを返す。ブラウザの価格は信用しない。
  2. 購入者が見積もりを確認して注文を作る。見積もり失効・価格変更時は再確認を要求する。注文と注文明細をトランザクションで保存する。
  3. 注文IDと決済試行番号を冪等キーにしてCheckoutを作成する。通信失敗時は同じキーで再試行し、二重セッションを防ぐ。結果不明の間は新しい決済試行を作らない。
  4. 決済事業者からのWebhookを生の本文で署名検証し、イベントIDを一意保存して受付する。永続化できない場合は成功応答せず、再送を受ける。
  5. ワーカーが決済の最新状態を照会し、注文との紐づけ・通貨・金額・入金済みを照合する。同一トランザクションで支払済み状態、購入権限、通知Outboxを記録する。セッション完了だけでは入金済みとしない。
  6. 戻り画面は注文APIを確認し、入金確認中なら時間を置いて再取得する。支払済みの場合にダウンロードを表示する。通知メールの障害は購入確定に影響させない。

状態の分離

対象状態と遷移例外の扱い
注文pending → confirmed / canceled遅れて入金を確認した注文は照合後にconfirmedへ復旧する。キャンセル表示だけで入金を破棄しない。
決済試行created → processing → paid / failed / expired
paid → refund_pending → refunded		失敗・期限切れで再試行可能。paidを古いイベントで未払いに戻さない。返金失敗時はpaidへ戻す。
購入権限active → suspended / revoked
suspended → active / revoked		返金要求時にsuspended、返金成功でrevoked、失敗確認後にactiveへ戻す。返金済み注文を遅い入金イベントで再有効化しない。

ダウンロード

認証済み利用者 → APIで注文の所有者・入金・有効な購入権限・購入時のファイルバージョンを確認 → 5分有効の署名付きURL → 非公開ストレージから取得。URLはログへ残さず、発行応答はキャッシュ禁止とする。署名付きURLは期限内の共有を完全には防げない。返金後も発行済みURLは最長5分利用でき、取得済みファイルは回収できない。

返金・異議申し立て

管理者が理由を入力 → 権限を一時停止 → 冪等キー付きで返金要求 → 通知または照会で結果確定 → 全額返金なら権限取消。タイムアウトは結果不明として照合し、再請求・再返金を避ける。異議申し立ては権限を一時停止し、運営へ通知する。解決結果と販売条件に基づき再開または取消を記録する。

08 認証と権限（本番向け設計）

  • 購入者はメール認証を行い、短時間・一回限りのログインリンクまたはコードを用いる。失敗回数を制限し、メールの登録有無を応答で漏らさない。
  • セッションはSecure・HttpOnly・SameSite属性のCookieで管理する。失効・ログアウト・管理者権限変更をサーバーで反映する。トークンはlocalStorageへ保存しない。
  • 管理者はMFA必須。返金は再認証を要求し、役割判定はAPIで実施する。商品管理者には返金権限を与えない。
  • HTTPS、CSRF、CSP、出力エスケープ、許可リスト型入力検証、SQLパラメータ化、認証・問い合わせ・ダウンロードの回数制限を設ける。
  • Webhook署名検証用の秘密鍵とAPIキーは秘密情報管理サービスに保存し、フロントエンドやGitに含めない。本番とテストで鍵を分離する。
  • 販売用バケットは公開禁止。アップロードはPPTXの内部構造・拡張子・実形式・サイズ・マルウェアを検証し、ZIP展開量を制限する。画像は安全な形式に再生成し、未検証SVGを公開しない。
  • カード情報は自社画面・API・ログで取り扱わず、決済事業者の画面へ入力する。ログに秘密鍵・認証リンク・署名付きURL・カード情報を記録しない。

10 テストと移行（本番向け設計）

ケース受入条件
通常購入・別端末テスト決済成功後に注文・権限・メールが整合し、同じアカウントから再取得できる。
価格改ざん・変更・販売停止送信価格を採用せず、変更は再確認。非公開商品を新規購入できない。
二重クリック・Webhook重複・順不同決済、権限、通知ジョブは重複しない。返金後に入金イベントを再送しても権限を復活させない。
偽Webhook・他人の注文署名不正は拒否。他人のIDを指定しても注文・PPTXを取得できない。
決済失敗・離脱・通知遅延未入金で取得不可。遅延入金は照合で復旧し、重複請求をしない。
返金・通信タイムアウト・異議申し立て結果不明を追跡し、返金成功で権限取消、失敗で復旧。再送で二重返金しない。
期限切れ・ファイル更新URLの期限切れ後は再発行。商品更新後も購入時のファイルを取得できる。
メール・DB・ストレージ障害購入記録を失わず再試行できる。障害時に権限を迂回しない。バックアップから復元可能。
管理・アップロード・スマートフォン権限外操作を拒否し、不正ファイルを公開しない。購入経路をモバイルとキーボードで完了できる。

開発・移行の順序

  1. 販売条件・基盤を確定し、DB・API・認証を構築する。
  2. 6商品をDBへ登録。販売用PPTXを非公開保存し、公開サンプルと販売商品を明確に分ける。
  3. 見積もり・注文・テスト決済・Webhook・購入権限を実装する。
  4. 履歴・メール・管理画面・返金・問い合わせを実装する。
  5. 監視・復元・権限テスト・販売表示を確認し、本番設定へ切り替える。
  6. 公開済み販売ファイルを配信元とビルド成果物から除去し、CDNキャッシュも削除する。過去に取得された公開サンプルは回収できないため、有料版は別ファイルとして扱う。
  7. 本番決済の検証手順と返金手順を運営者が確認した後に販売を開始する。

現在のローカル実装は型チェック・ビルド・PC／モバイル計14件・サーバー・ファイル処理テスト10件・実ツール確認2件を確認済み。本番の認証・実決済・外部配信・性能は別途テストする。localStorageのデモ注文から本番の購入権限は発行しない。
