1. この資料の前提と調査範囲

販売する商品、規模、予算が未定のため、日本国内向け・単一店舗・一般消費者向けの物販を基準に整理する。デジタル商品、定期購入、複数出店者のサイトとの差分も扱う。

この資料は一般的なECの設計知識を整理したもので、個別サイトの実測比較や最新の市場調査ではない。外部資料の取得を試みたが、環境のネットワーク制限によりHTTPプロキシから403が返り、本文を確認できなかった。そのため、普及率・売上への効果・最新料金についての数値は載せていない。末尾の参考URLは追加調査先として掲載する。

パターン 主な用途 特有の機能・設計 初期開発の負担

3. 画面構成と購入フロー

標準的な画面

画面 主な内容 設計上のポイント
トップ ブランド紹介、カテゴリ、特集、人気商品 最初の画面で何を販売しているか伝わる
商品一覧・検索結果 商品画像、名前、価格、在庫、絞り込み、並び替え 商品数が少ない段階では絞り込みを増やしすぎない
商品詳細 画像、説明、価格、選択肢、在庫、送料、配送目安 サイズ・色などを選択してからカートへ追加する
カート 商品、数量、小計、送料の見込み 数量変更・削除・購入への移動を分かりやすくする
チェックアウト 連絡先、配送先、配送方法、支払い、最終確認 総額と注文条件を確定前に確認できる
注文完了 注文番号、購入内容、配送予定、問い合わせ先 決済状態をサーバー側で確認して表示する
マイページ 注文履歴、住所、会員情報 初期段階では会員機能を省略してもよい
ご利用ガイド 配送、支払い、返品、問い合わせ 購入前に不明点を解消できる
法定・ポリシーページ 特商法表記、プライバシー、利用規約等 実際の運営・販売条件と一致させる
管理画面 商品、在庫、注文、出荷、返金 購入者の画面と権限を分ける

よくある購入の流れ

トップ／検索 → 商品一覧 → 商品詳細 → カート
  → 配送先入力 → 配送・支払い方法の選択 → 注文内容の最終確認
  → 支払い → 注文完了 → 確認通知 → 出荷通知

外部の決済画面を利用する場合は、配送先入力や最終確認を決済サービス側で担当することもある。画面の分担は、採用するサービスと日本向けの表示要件を確認して決める。

チェックアウトの代表的な形式

形式 向いているケース 注意点
1ページ形式 入力項目が少ない購入 モバイルで長くなりやすく、エラー位置を見つけやすくする必要がある
ステップ形式 配送・支払いの選択が多い購入 現在位置、残りの手順、入力内容の保持が必要
決済サービスのホスト画面 決済を早く導入したい場合 ブランド表現や入力項目の自由度、画面分担を確認する

ゲスト購入を基本にすると、会員登録を購入の前提にせずに済む。会員化が必要なら、購入後の登録導線も検討する。

4. デザイン・操作でよくあるパターン

  • カテゴリ中心： 商品の種類から探す。カテゴリ名は購入者が理解できる言葉にする。
  • 検索中心： 商品数が多い場合に適する。検索語の保持、該当なしの案内、条件解除を用意する。
  • 特集・ストーリー中心： ブランドや用途から商品を提案する。読み物から商品詳細へ進めるようにする。
  • 商品カードの統一： 画像比率、商品名、価格、販売状態を揃え、比較しやすくする。
  • モバイルを前提にする： タップ領域、画像の読み込み、フォームの入力補助を整える。
  • 購入判断の情報を近くに置く： 送料、配送目安、返品条件を購入ボタンの周辺から確認できるようにする。
  • アクセシビリティを基本にする： キーボード操作、フォームのラベル、明確なエラー、色だけに頼らない状態表示を用意する。

レビュー、ランキング、おすすめ商品、お気に入りは追加候補。実際の投稿や注文データがない段階で、架空のレビューや人気順位を表示しない。

6. 初期版（MVP）に含める機能

初期版の候補

  1. 商品一覧・詳細。必要な商品画像、説明、価格、在庫を表示する。
  2. サイズ・色などの商品バリエーション。商品に不要なら省略する。
  3. カートの追加・数量変更・削除。
  4. ゲスト購入、配送先入力、送料計算、注文内容の最終確認。
  5. 決済サービスによる支払いと、Webhookによる結果の確定。
  6. 在庫不足の判定と、注文・在庫更新の整合性維持。
  7. 注文完了表示、注文確認通知、出荷通知。
  8. 商品・在庫・注文を管理する機能。
  9. 配送、返品、問い合わせ、法定表記、プライバシーの案内。

後から追加しやすい機能

会員登録、お気に入り、レビュー、クーポン、ポイント、レコメンド、高度な検索、多言語、多通貨、定期購入、外部倉庫連携。販売モデルに必須のものは初期版へ繰り上げる。

初期版でも、支払い失敗、返品・返金、出荷変更を扱う運用手順は必要。管理画面を簡略化する場合は、決済サービスの管理画面などで代替できる操作を明確にする。

7. データと業務処理の基本パターン

データ 主な役割
商品 名前、説明、画像、公開状態、カテゴリ
SKU／バリエーション サイズ・色の組み合わせ、価格、販売可能な単位
在庫 SKUごとの在庫数、引当数、更新履歴
カート・カート明細 購入候補と数量。最終価格の確定前の状態
注文・注文明細 購入時点の商品名、単価、税、送料、合計、購入条件を保存
決済 決済サービスの識別子、金額、状態、返金情報
配送 配送先、配送状態、追跡番号
購入者 会員の場合のアカウント。ゲスト注文の連絡先は注文側にも保持

設計時に外せない点

  • 価格はサーバーで再計算する。 ブラウザから送られた単価や合計を信用しない。通貨に応じた最小単位の整数などを使い、浮動小数点の誤差を避ける。
  • 注文時の情報を保存する。 商品情報が更新されても過去の注文内容が変わらないようにする。
  • 在庫は同時購入を考慮する。 トランザクションや条件付き更新で売り越しを防ぐ。引当のタイミングと期限、失敗時の解放を決める。
  • 決済は画面への戻りだけで確定しない。 署名を検証したWebhookなどで結果を確認する。決済方法によっては完了通知が後から届く。
  • 同じ処理が繰り返されても重複させない。 決済要求・Webhook・通知・在庫更新に冪等性を持たせる。重複と順序の入れ替わりを想定する。
  • 注文・決済・配送の状態を分ける。 「決済済み・未出荷」「一部返金・配送済み」などを表現できるようにする。
  • 通知失敗と注文失敗を分ける。 メール送信の障害で決済済み注文を失わないようにし、通知を再送できるようにする。

基本的な状態の例：

注文：受付待ち → 受付済み → 完了／キャンセル
決済：未払い → 処理中 → 支払済み／失敗 → 一部返金／返金済み
配送：未出荷 → 準備中 → 出荷済み → 配送済み

実際の遷移は販売モデルに合わせる。例えば、返金と返品は別の処理であり、返金しただけで在庫を自動的に戻す設計にはしない。

8. 日本向け販売で検討する項目

  • 消費税込み価格、送料、手数料、割引後の最終支払額の表示。
  • 軽減税率対象商品など、商品による税率の違いと端数処理。
  • 郵便番号、都道府県、建物名などを含む住所入力。
  • クレジットカード以外の決済方法と、未払い・入金待ちの扱い。
  • 配送可能地域、送料条件、送料無料の条件、発送までの日数。
  • 特定商取引法に基づく表示と、注文の最終確認画面で必要になる表示。
  • 返品・キャンセル条件、問い合わせ窓口、個人情報の利用目的。
  • インボイス対応や領収書の必要性。扱う商品・販売先によって判断する。

法律・サービス仕様に依存する項目は、公開前に最新の一次資料と実際の運用条件を照合する。特に通信販売の返品条件は、他の販売形態のルールをそのまま当てはめない。

9. 開発・公開前に確認する代表的なケース

ケース 確認する結果
通常購入 正しい合計で決済され、注文・在庫・通知が一致する
決済失敗／離脱 支払済みと表示されず、在庫引当を適切に解放する
二重クリック／Webhook再送 注文・請求・通知・在庫更新が重複しない
在庫残り1点への同時購入 在庫を超える注文を確定しない
カート投入後の価格・在庫変更 最新条件を確認し、購入者へ変更を伝える
不正な単価・数量の送信 サーバー側で拒否または正しい条件へ再計算する
他人の注文URLへのアクセス 注文情報を取得・変更できない
メール送信の障害 注文は保持され、通知を再実行できる
キャンセル／一部返金 決済、注文、返品後の在庫が業務ルールと一致する
モバイル・キーボード操作 商品選択から購入まで操作でき、入力エラーを理解できる

学習用・デモでは決済サービスのテストモードを使う。実販売前には、本番の配送・税・問い合わせ・通知・障害対応を確認する。

更新日：2026年10月1日。対象は単一店舗のPowerPoint資料販売デモで、配送・物理在庫はありません。費用と外部サービス登録が発生しないローカル実装を先行しています。

販促・分析 お気に入り、並び替え、クーポン・セット、日別イベント件数 会員に紐づく保存、実販売向け分析の同意と精度

バックエンドの価格計算・重複防止・購入時スナップショットは実装済みですが、実入金を確定する処理は未実装です。ストレージ署名付きURLとローカルAPIトークンの違い、実際のSQLite構成、画面・APIパスは ローカル基本設計 に記載しています。

次に決める事項は、販売者情報と販売条件、本人認証・決済・配信の提供事業者、予算、本番の保存期間・障害対応体制です。本番の構成案は 基本設計書（HTML）、初期静的デモは 設計履歴 を参照してください。
